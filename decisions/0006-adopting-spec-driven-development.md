# ADR 0006: Adopting GitHub Spec Kit's Spec-Driven Development conventions

**Status:** Accepted
**Date:** 2026-08-04

## Context

Before pushing this repo publicly, the request was to align it with the
standards defined in [github/spec-kit](https://github.com/github/spec-kit) —
GitHub's Spec-Driven Development (SDD) toolkit. Spec-kit is a methodology,
not a linter: it defines a `.specify/memory/constitution.md` of
non-negotiable articles, a `specs/[number]-[name]/` structure
(spec.md → plan.md → tasks.md) for every feature, and a set of
`/speckit.*` commands (via an installable CLI) that generate and enforce
that structure.

Two constraints shaped how this was adopted rather than just described:

1. **No network access in the environment that built this.** The actual
   `specify` CLI (`uv tool install specify-cli`) could not be installed
   or run. Every file in `.specify/` here was hand-authored to match the
   *documented* structure and conventions, not generated by the tool
   itself. This is disclosed plainly in `.specify/README.md` so nobody
   mistakes this for a CLI-generated tree.
2. **Spec-kit's nine articles are written for application backends**
   (Library-First, CLI Interface Mandate, Test-First, Integration-First
   Testing against real databases). This repo ships CSS tokens and
   component classes, not services. Rather than force a literal,
   nonsensical mapping (e.g. requiring every palette to expose a
   command-line interface), each article was translated honestly to
   this domain in `.specify/memory/constitution.md`, with the mapping
   stated explicitly rather than left implicit.

## Decision

- Adopt `.specify/memory/constitution.md` as the supreme governance
  document, ranking above `AGENTS.md` and `CONTRIBUTING.md` on conflict.
- Adopt `.specify/templates/{spec,plan,tasks,checklist}-template.md` for
  all future feature work.
- Retrofit v1 into `specs/001-design-system-foundation/` as both a
  historical record and the worked example future specs should follow —
  explicitly marked as a retrofit, not a spec written before the fact,
  so no one mistakes the sequencing.
- Keep `decisions/*.md` (this ADR log) as a complementary record of
  *why*, distinct from the constitution's *what's non-negotiable*. The
  constitution doesn't replace the ADR log; spec-kit doesn't define an
  ADR concept of its own, and nothing about adopting it requires
  discarding one that was already working.

## Consequences

- Every new feature (a new product theme, a new shared component) now
  has an explicit template to follow: `specs/00N-name/spec.md` → `plan.md`
  (with a Constitution Check gating on Articles VII–IX) → `tasks.md`.
- The existing `scripts/check-contract.js` and `scripts/lint-boundaries.js`
  are now explicitly the mechanical enforcement of Articles II, III, IV,
  and VI — they didn't need to change, but their *authority* is now
  constitutional rather than just "a script someone wrote."
- If this project later runs the real `specify` CLI, it may try to write
  its own scaffolding (agent prompt files, helper shell scripts) into
  `.specify/`. `.specify/README.md` flags the one file that must not be
  silently overwritten: `memory/constitution.md`, which is ratified
  content, not a template — this mirrors a known failure mode
  (spec-kit's own issue #391) where the installer can clobber a
  real constitution with its placeholder template.
- This ADR itself is an example of Article II in miniature: the decision
  to adapt rather than force-fit the nine articles is written down
  rather than left as an implicit judgment call a future agent would
  have to reverse-engineer.

## Alternatives considered

- **Install and run the actual `specify` CLI.** Not possible — no
  network access in this environment. Flagged rather than silently
  worked around.
- **Copy spec-kit's own constitution.md verbatim, articles I–III and
  VII–IX unchanged.** Rejected — several of its literal requirements
  (e.g., "every library exposes a CLI accepting stdin/stdout") don't
  describe anything meaningful for a CSS token package, and pretending
  otherwise would produce a constitution nobody actually follows, which
  is worse than an honestly adapted one.
- **Treat spec-kit as advisory only; change nothing structural.**
  Rejected — the request was explicit about following its standards
  before pushing, and a constitution that isn't wired into real
  enforcement scripts and a real `specs/` folder would be decoration,
  not governance.
