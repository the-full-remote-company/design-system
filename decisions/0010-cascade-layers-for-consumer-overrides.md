# ADR 0010: CSS cascade layers for consumer overrides

**Status:** Accepted
**Date:** 2026-09-01

## Context

This design system's CSS ships unlayered. Every consumer's own utilities —
whether hand-written or generated by a framework like Tailwind v4 — sit in
an unlayered `@layer` bucket too, but the cascade doesn't compare layers
before it compares specificity when neither side is layered; it just
falls back to source order and specificity as if layers didn't exist. In
practice that means an unlayered design-system rule beats an unlayered
utility rule of equal or lower specificity whenever the design-system's
stylesheet is linked after the utility one, which is the common case
since a consumer typically imports the design system first and their own
styles on top.

Concretely: a consumer using Tailwind cannot reliably override
`.btn--primary` with a `bg-*` utility — both are single-class selectors,
so it comes down to source order, which the consumer does not control
once the design system is imported first. `.field input` is worse: two
class-less type/attribute selectors compound to (0,1,1), beating any
single-class utility outright regardless of import order.

This has been reachable since `decisions/0007.md` let products install
these packages instead of copy-pasting the CSS inline where they could
freely reorder or edit it. It stayed theoretical while `consumers:
none_yet` — nobody has hit it yet. It stops being theoretical the moment
a real consumer needs to override one line of shipped CSS, which is
normal and expected for a design system, not a misuse of one. Doing
nothing means the first consumer to try discovers this by fighting the
cascade with `!important` or ever-more-specific selectors, which is
exactly the failure mode cascade layers exist to prevent.

## Decision

Every layered stylesheet in this system declares its layer explicitly,
using the same two layer names in every package so a consumer only needs
to learn the scheme once:

- **`@layer base`** — the reset and accessibility floor in
  `packages/foundation/src/base.css` (the universal box-sizing rule, the
  `:focus-visible` outline, and the reduced-motion block).
- **`@layer components`** — every component file: `@tfrc/marketing`'s and
  `@tfrc/product`'s `components.css`, and theme-level component additions
  such as `finance.css`'s `.theme-tag`.
- **Custom property declarations stay unlayered.** Both `:root` blocks in
  `base.css` (spacing scale, easing shapes), every package's
  `tokens.css`, and `finance.css`'s theme-identity `:root` block are
  deliberately left outside any `@layer` block.

Each package's `src/index.css` declares the layer order as its first
line — `@layer base, components;` — so the order is registered even if a
consumer imports one file directly instead of the package entry point,
since a layer's position in the cascade is fixed by the first place it is
*named*, not the first place a rule is written into it.

Consumers are expected to declare their own utility layer after these
two — `@layer base, components, utilities;` — which is now documented in
`CONSUMING.md` and mechanically checked by `tfrc-verify`'s new
`LAYER_ORDER` rule (Article II: a rule a consumer could break gets a
check, in the same PR).

## Consequences

- A consumer's utility layer now reliably wins the cascade against this
  system's components and reset, regardless of specificity or import
  order, once they declare `@layer base, components, utilities;` and
  place their utility rules in the third layer. This is the entire point:
  overriding this design system becomes a normal, supported act instead
  of a specificity fight.
- **Custom properties are unlayered on purpose, and this is the sharpest
  edge in this decision.** If `:root` custom-property declarations were
  layered, any unlayered `:root` block in a consumer's own CSS — which is
  extremely common, since most authors have never had a reason to think
  about layering a `:root` block — would silently win over the design
  system's token values, because an unlayered declaration always beats a
  layered one at equal specificity. That would make theming (swapping a
  palette, applying a product theme) unpredictably fragile depending on
  what a consumer happened to also define at `:root`, for a reason
  invisible in the consumer's own file. Leaving custom properties
  unlayered keeps their resolution governed by ordinary specificity and
  source order, which is the behavior every existing theme
  (`decisions/0001.md`, `decisions/0005.md`) was already built assuming.
- **This is a behavioral change**, not merely an additive one: the reset
  and component rules move from unlayered (highest cascade priority
  among equal-origin rules) into named layers (lowest priority among
  equal-origin rules, below anything unlayered). Any consumer currently
  relying on this system's unlayered components.css beating their own
  unlayered override would see that override start winning after
  upgrading. `STATE.md` records `consumers: none_yet` as of this ADR —
  which is exactly why this is the moment to make the change: there is no
  one to break yet, and the packages are still pre-1.0-consumer in every
  sense that matters even though they've been published. Package versions
  bump MINOR, not MAJOR, on that basis (no real consumer's rendered output
  changes), but the change is recorded here as behavioral rather than
  purely additive so a future reader doesn't mistake it for a no-op.
- Every consumer must now declare `@layer base, components, utilities;`
  (or equivalent, naming these two layers first) before their own styles
  will layer correctly against this system. Skipping that declaration
  doesn't error — the layers still exist, just implicitly ordered by
  first-encounter, which can silently reproduce the old unlayered
  behavior or something else entirely depending on import order. This is
  exactly the gap `tfrc-verify`'s new `LAYER_ORDER` rule and
  `CONSUMING.md`'s worked example exist to close.
- `packages/foundation/src/base.css`'s two `:root` blocks and every
  `tokens.css` file remain unlayered, and `packages/product/src/themes/
  finance.css`'s `:root` block does too — none of this needed to change,
  which keeps this ADR's blast radius to exactly the reset and the
  component layers.

## Alternatives considered

- **Consumer-side `@import url(...) layer(...)`.** CSS already lets an
  *importer* assign an imported, unlayered stylesheet to a layer at the
  `@import` site, without the imported file changing at all. Rejected as
  the sole mechanism: it works, but it means every consumer independently
  rediscovers this exact problem, writes their own `layer()` wrapping,
  and gets it right or wrong on their own — the opposite of "one product
  system, not one per product" (`decisions/0001.md`). Declaring the
  layers inside the shipped CSS means a consumer who does nothing extra
  still gets correctly-layered output; a consumer who wants to name their
  own additional layers still can, on top.
- **`!important` on consumer overrides.** Not a decision so much as the
  status quo failure mode this ADR exists to remove. Rejected outright:
  it doesn't compose (the next override needs `!important` too, or
  higher specificity than that), and it's exactly the kind of escalating
  specificity war cascade layers were added to CSS to end.
- **Layer the custom-property `:root` blocks along with everything
  else**, for consistency with base/components. Rejected — see
  Consequences above. Consistency for its own sake is not worth making
  every theme's token resolution depend on whether a consumer's own
  `:root` block happens to be layered, which most authors have no reason
  to have considered.
- **Do nothing until a real consumer hits it.** Rejected: `CONSUMERS.md`
  already names two imminent consumers, and this is exactly the kind of
  behavioral change (Consequences, above) that is far cheaper to make
  before a real consumer exists to be broken by it than after.
